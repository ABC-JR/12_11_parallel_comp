The ridge point is calculated as:

\[

\[
I^* = \frac{0.2303}{4.7499}

\]

The compute-ceiling benchmark is a Python-level scalar arithmetic benchmark. Its result is an empirical ceiling for this particular implementation and runtime, not the processor's theoretical hardware peak FLOP/s.

### 4.5 Part 3B — Progressive GEMM

Three matrix multiplication implementations were evaluated using 256 × 256 double-precision matrices.

The total number of floating-point operations was calculated using:

\[
FLOPs = 2N^3
\]

For N = 256:

\[
FLOPs = 2 \times 256^3
\]

### 4.6 GEMM Variant Comparison

| Variant | Loop Order | Median Time (s) | Performance (GFLOP/s) |
|---|---|---:|---:|
| Variant 1 | Naive i-j-k | 0.627481 | 0.053475 |
| Variant 2 | Reordered i-k-j | 0.891388 | 0.037643 |
| Variant 3 | Cache-Blocked, BS=96 | 1.016906 | 0.032997 |

In this run, the naive implementation was the fastest.

Reordering and cache blocking did not improve execution time in this Python implementation. Although i-k-j gives unit-stride access to rows of B, it also performs repeated updates to C and incurs Python interpreter and loop overhead.

The blocked implementation adds further tile-loop overhead. For this relatively small 256 × 256 matrix, those overheads can outweigh the locality benefit.

These results should not be interpreted as evidence that cache blocking is generally slower. They show that, for this matrix size and this pure-Python implementation, the expected memory-locality benefit did not compensate for additional interpreter-level loop overhead.

The tile footprint is calculated using:

\[
W_{tile}(BS)=3\times BS^2\times8

\[

\[

## 5. Phase 4 — Skewed Workloads and Dynamic Chunk Queue

**Status: Pending implementation and measurement.**

### 5.1 Experimental Configuration

The experiment uses a skewed workload of 8,000 items distributed across 8 physical workers.

Each item performs a variable amount of computation defined by:

\[
K(i)=1+\left\lfloor\left(\frac{i}{40}\right)^2\right\rfloor
\]

The computation includes heavy trigonometric operations such as:

- `sin()`
- `cos()`
- `sqrt()`

### 5.2 Scheduling Strategies

Three scheduling approaches will be compared:

1. **Contiguous Block Static Scheduling**

   The workload is divided into contiguous blocks, and each worker processes its assigned block.

2. **Cyclic Round-Robin Static Scheduling**

   Items are distributed cyclically across workers.

3. **Dynamic Shared-Memory Queue**

   Workers obtain the next available chunk through a synchronized shared counter.

The dynamic queue will be tested with:

\[
C\in\{1,8,64,512\}
\]

### 5.3 Required Measurements

The following measurements will be added after running `task4_scheduling.py`:

- Wall time for contiguous block static scheduling.
- Wall time for cyclic round-robin static scheduling.
- Dynamic queue wall times for chunk sizes C = 1, 8, 64, 512.
- Per-worker active runtimes.
- Load imbalance factor.
- Selected optimal chunk size C*.
- Explanation of synchronization contention versus tail imbalance.
- Phase 4 verification tag.

### 5.4 Load Imbalance Factor

The load imbalance factor is calculated using:

\[
\lambda =
\frac{\max_{0\leq t<p}t_{\mathrm{worker}[t]}}
{\frac{1}{p}\sum_{t=0}^{p-1}t_{\mathrm{worker}[t]}}
\]

A value of \(\lambda\) close to 1 indicates a balanced workload.

A larger value indicates that some workers spend significantly more time processing their assigned items than others.

### 5.5 Expected Scheduling Trade-Off

A small chunk size such as C=1 provides fine-grained load balancing, but requires frequent synchronization and access to the shared queue.

A large chunk size such as C=512 reduces synchronization overhead, but can create tail imbalance because workers may receive chunks with significantly different computational costs.

The optimal chunk size C* will be selected from the actual measured wall times and load imbalance values.
